# Engineering Case Studies

## 1. 프레임과 시뮬레이션 시간 분리

### 문제

패킷, 트래픽, 노드와 엣지가 각자의 `Update` 흐름에 의존하면 프레임 상황에 따라 처리 순서와 계산 단위가 달라지고 디버깅 범위가 넓어집니다.

### 접근

`Simulation`에 `fixedDt = 0.1f` 기반 누적 루프를 두고, 한 곳에서 `SimulationEventBus.RaiseTick(dt)`를 발생시키도록 만들었습니다. 노드와 엣지는 이 틱을 구독해 동일한 시간 단위로 상태를 갱신합니다.

### 결과

- 렌더링과 게임 규칙의 시간축 분리
- 패킷 처리 흐름을 하나의 틱 단위로 추적 가능
- 배속 기능이 시뮬레이션 진입점 한 곳에 모임

## 2. 라우팅 알고리즘의 교체 비용 줄이기

### 문제

라우터 내부에 다음 홉 선택 규칙을 직접 구현하면 새로운 알고리즘을 실험할 때 노드의 패킷 처리 코드까지 수정해야 합니다.

### 접근

선택 규칙을 `INextHopPolicy`로 추상화하고 `RoundRobinPolicy`, `BestStatePolicy` 구현으로 분리했습니다. 노드는 현재 설정에 맞는 정책 인스턴스에 후보 선택을 위임합니다.

### 결과

- 패킷 처리 과정과 경로 선택 규칙 분리
- 기존 노드 흐름을 유지하면서 정책 추가 가능
- 정책별 동작을 좁은 범위에서 비교·검증 가능

## 3. 네트워크 장애를 데이터로 확장하기

### 문제

DDoS, 트래픽 버스트, 링크 장애를 하나의 컨트롤러 조건문으로 계속 추가하면 대상 선택, 지속 시간, 시작·종료 처리의 분기가 빠르게 늘어납니다.

### 접근

공통 수명 주기를 가진 `NetworkIncidentSO`를 만들고 장애별 구현을 ScriptableObject로 분리했습니다. 컨트롤러는 어떤 장애인지보다 시작·진행·종료 시점을 관리하는 역할에 집중합니다.

### 결과

- 장애별 효과 로직을 독립된 파일과 에셋으로 관리
- 스테이지 데이터에서 장애 조합과 타이밍 구성 가능
- 종료 시 상태 복구 책임을 각 장애 구현에 명확히 배치

## 4. UI와 게임 상태의 의존성 관리

### 문제

HUD와 정보 패널이 시뮬레이션 내부 객체를 직접 참조하면 UI 추가·교체가 코어 코드 변경으로 이어지고, 씬 전환 시 구독 수명 관리도 어려워집니다.

### 접근

네트워크, 경제, 미션, 건설, 선택 이벤트를 도메인별 버스로 분리했습니다. UI 컴포넌트는 활성화 시 필요한 이벤트를 구독하고 비활성화 시 해제합니다.

### 결과

- 코어가 구체적인 UI 컴포넌트를 알지 않음
- HUD, 정보 패널, 튜토리얼이 같은 상태 변화를 독립적으로 소비
- 이벤트 책임과 구독 위치를 도메인 단위로 탐색 가능
