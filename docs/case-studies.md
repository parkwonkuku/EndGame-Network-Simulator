# Engineering Case Studies

## 1. Additive 씬 로드에서 초기화 순서 보장

### 문제

공통 게임 시스템과 스테이지 맵을 별도 씬으로 구성하자 `GameCore` 오브젝트의 `Start()`가 맵 씬 로드와 그리드 등록보다 먼저 실행되는 경우가 생겼습니다. 초기 사용자와 서버가 아직 없는 맵을 참조하거나, 카메라 전환 중 무거운 씬 활성화가 겹쳐 연출 프레임이 끊겼습니다.

### 해결

씬 전환을 `SceneLoadCoordinator` 한 곳으로 모았습니다. 공통 씬 로딩은 카드 전환 연출과 병렬로 진행하되 실제 활성화는 연출 뒤로 미루고, 맵 씬을 Additive로 붙인 다음 한 프레임을 더 기다려 `GameBootstrapper.BeginGame()`을 명시적으로 호출했습니다. `GameBootstrapper`도 중복 시작을 막는 가드를 두었습니다.

### 결과

- 맵과 공통 시스템의 로드 순서가 Unity 이벤트 실행 순서에 의존하지 않음
- 같은 조립 흐름으로 일반 스테이지와 튜토리얼을 시작
- 씬 활성화와 카메라 전환의 프레임 경합 완화

## 2. 케이블 미리보기·결제·환불 불일치 제거

### 문제

케이블은 기존 선에서 분기하거나 여러 세그먼트가 같은 셀을 공유할 수 있습니다. 입력, 미리보기, 확정, 철거 코드가 비용을 각각 계산하면 조인트 셀 이중 과금, 표시 금액과 실제 차감액 불일치, 업그레이드 후 낮은 금액 환불 같은 문제가 발생했습니다.

### 해결

`BuildTransactionService`가 검증, 비용 계산, 경제 이벤트와 영구 상태 변경을 전담하도록 했습니다. `CalculateCableCost`를 미리보기와 확정이 함께 사용하고, `CableGraph`에 셀별 실제 지불 금액을 기록했습니다. 일반 셀은 전체 그래프에서 한 번만 과금하고 노드 끝점은 케이블별 과금 규칙을 적용했습니다. 업그레이드는 등급 간 차액만 받고 지불 기록도 새 단가로 갱신합니다.

### 결과

- UI 예상 비용과 확정 결제 금액이 같은 계산 경로 사용
- 공유 셀과 분기점의 중복 과금 방지
- 부분 철거와 업그레이드 이후에도 실제 지불액 기준 환불
- 입력 컨트롤러는 초안 처리, 서비스는 상태 변경이라는 책임 경계 확보

## 3. Steam 계정과 Unity 서비스의 사용자 식별 통합

### 문제

익명 Unity Authentication만 사용하면 세션 토큰이 삭제되거나 다른 PC에서 실행했을 때 기존 Cloud Save와 랭킹의 `PlayerId`에 다시 접근할 수 없습니다. 또한 데모와 본편은 Steam App ID가 달라 티켓을 다른 앱 설정으로 검증하면 인증이 거부됩니다.

### 해결

`ApplicationBootstrapper`가 현재 출시 타입의 App ID로 Steam을 먼저 초기화한 뒤 저장과 온라인 서비스를 준비하도록 순서를 고정했습니다. `SteamManager`에서 Web API 인증 티켓을 발급하고, 동일한 identity와 App ID를 `SignInWithSteamAsync`에 전달했습니다. 티켓은 검증이 끝나기 전에 취소되지 않도록 수명을 유지하며, Steam을 사용할 수 없는 개발 환경이나 인증 실패 시에는 익명 로그인으로 폴백합니다.

### 결과

- 클라우드 진행도와 랭킹 ID를 Steam 계정에 연결
- 데모·본편 App ID를 하나의 코드베이스에서 안전하게 분리
- 온라인 인증 실패가 게임 실행 실패로 번지지 않음

## 4. 클라우드 저장 실패에도 진행도 보존

### 문제

저장할 때 클라우드 요청부터 수행하면 네트워크 장애 동안 진행도를 잃을 수 있습니다. 반대로 비동기 업로드 중 사용자가 다시 저장하면 먼저 시작한 요청의 완료 콜백이 최신 저장까지 동기화된 것으로 잘못 표시할 위험이 있습니다.

### 해결

모든 저장을 로컬에 먼저 기록하고 클라우드 사용 시 `hasPendingCloudSave`를 함께 남겼습니다. 각 로컬 저장에 증가하는 버전을 부여해, 업로드가 성공해도 요청 당시 버전이 현재 버전과 같을 때만 pending 상태를 해제합니다. 실패한 데이터는 로컬에 남겨 다음 실행 시 클라우드 로드보다 먼저 재전송합니다.

### 결과

- 오프라인과 서비스 장애 중에도 로컬 진행도 유지
- 늦게 완료된 이전 요청이 최신 저장 상태를 덮어쓰지 않음
- 다음 실행에서 미전송 저장을 자동 복구

## 5. 행동이 아닌 네트워크 완성 상태로 튜토리얼 판정

### 문제

“라우터 버튼 클릭”, “케이블 설치 완료” 같은 UI 이벤트만 세면 잘못 연결된 망도 튜토리얼을 통과할 수 있었습니다. 분배기와 병합기 실습은 필요한 장비 수만 맞아도 실제 병렬 경로가 완성되지 않을 수 있습니다.

### 해결

`TutorialConditionEvaluator`가 시뮬레이션 그래프를 직접 탐색하도록 했습니다. 사용자에서 서버까지 진입 가능한 엣지만 따라가며 색상 일치 여부를 확인하고, 분배기의 서로 다른 출력이 서로 다른 병합기를 거쳐 같은 목적 서버에 도달하는지도 검사합니다. 과부하 또는 draining 상태가 있으면 안정 시간을 초기화해, 완성된 망이 일정 시간 정상 동작해야 다음 단계로 넘어가게 했습니다.

### 결과

- UI 조작 순서와 무관하게 실제 학습 목표 달성 여부 판정
- 잘못된 색상 연결과 미완성 병렬 경로를 통과시키지 않음
- 병목 개선 결과를 플레이어가 관찰한 뒤 진행하는 재현 가능한 실습 구성
