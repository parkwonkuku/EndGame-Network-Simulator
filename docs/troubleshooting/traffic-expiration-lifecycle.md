# TTL 만료 통지와 네트워크 자원 회수 시점 분리

## S — Situation

트래픽에는 제한 시간이 있지만 패킷은 만료 순간에도 노드 대기열이나 전송 경로에 남아 있을 수 있습니다. TTL이 끝났다는 이유로 패킷을 즉시 제거하면 대기열 점유가 사라져 병목이 자연스럽게 해소되고, 플레이어가 네트워크 용량을 개선해야 한다는 설계 의도와 실제 상태가 어긋납니다.

반대로 실패 결과를 패킷마다 알리면 통계와 사운드가 중복될 수 있고, 풀 객체를 여러 소유자가 반환하면 이중 반환 위험이 생깁니다.

## T — Task

다음 시점을 분리해야 했습니다.

- TTL 초과를 실패 결과로 한 번 통지하는 시점
- 개별 패킷이 도착 또는 드롭되어 네트워크 소유권을 끝내는 시점
- 모든 패킷이 해결되어 `Traffic` 객체를 풀로 반환하는 시점
- 생성 도중 실패했을 때 이미 할당한 객체를 복원하는 시점

## A — Action

`Traffic.outcomeReported`를 결과 통지 가드로 두고, `IsResolved`는 도착 수와 드롭 수의 합이 전체 패킷 수에 도달했는지만 판단하도록 분리했습니다.

```text
PostTick에서 TTL 초과 발견
  -> state = Expired
  -> PublishTrafficOutcome(false)  // 한 번만 통지
  -> 패킷은 현재 소유자에 그대로 남음

각 패킷 도착/드롭
  -> Traffic 카운터 갱신
  -> PacketLifecycleService.Release
  -> 모든 패킷 해결 시 Traffic 풀 반환
```

패킷의 생성·소유권 이전·최종 반환은 `PacketLifecycleService`가 맡습니다. 드롭 이벤트 구독자에서 예외가 발생해도 `finally`에서 패킷을 반환하고 트래픽 완료 여부를 다시 검사합니다. 트래픽 생성 중 한 패킷이라도 풀에서 얻지 못하면 앞서 생성한 패킷을 모두 반환하고, 활성 트래픽 등록을 제거한 뒤 트래픽 객체도 반환합니다.

### 검토한 다른 방법

- 만료 즉시 모든 패킷 제거: 구현은 단순하지만 대기열 점유와 병목 상태를 함께 지우므로 제외했습니다.
- 통계용 만료 객체와 네트워크 패킷을 완전히 분리: 상태 표현은 명확하지만 별도 식별자 매핑과 정리 규칙이 늘어 현재 구조보다 복잡해집니다.
- 각 노드와 엣지가 직접 풀 반환: 소유권 책임이 분산되어 이중 반환과 누락을 추적하기 어려워 중앙 생명주기 서비스를 선택했습니다.

### 실패 시 처리

- 잘못된 크기·패킷 수 또는 풀이 없으면 트래픽을 시작하지 않습니다.
- 생성 도중 실패하면 그 요청에서 이미 만든 패킷과 트래픽 등록을 되돌립니다.
- 드롭 이벤트 처리에서 예외가 발생해도 패킷 반환과 최종화는 실행합니다.
- 만료 뒤에도 어떤 소유자에서도 도착·드롭되지 않는 패킷은 계속 활성 상태로 남을 수 있습니다. 이는 강제 정리 정책을 추가하기 전의 현재 제약입니다.

## R — Result

정적 코드 확인으로 TTL 만료 시 실패 결과는 한 번만 발행되고, 패킷은 각각 도착 또는 드롭될 때 반환되며, 트래픽은 모든 패킷이 해결된 뒤 제거되는 순서를 확인했습니다. 풀 할당 실패와 이벤트 예외 분기에도 반환 경로가 있습니다.
