# 비동기 저장 응답의 완료 상태 갱신 제한

## S — Situation

게임 진행도는 네트워크 상태와 관계없이 먼저 로컬에 남아야 했습니다. 동시에 클라우드 업로드를 기다리는 동안 사용자가 다시 저장하면 여러 요청이 겹칠 수 있습니다. 먼저 시작한 요청의 완료 응답이 늦게 돌아와 최신 저장까지 동기화된 것처럼 `hasPendingCloudSave`를 해제하면, 아직 업로드되지 않은 로컬 변경이 다음 실행에서 재시도되지 않을 수 있습니다.

## T — Task

- 모든 저장을 로컬에 먼저 반영한다.
- 클라우드 업로드가 필요한 로컬 데이터는 pending 상태로 남긴다.
- 이전 요청의 늦은 성공·실패 응답이 최신 pending 상태를 바꾸지 못하게 한다.
- 초기 클라우드 로드나 업로드가 실패해도 로컬 데이터로 진행한다.

## A — Action

`SaveLocal`에서 데이터를 먼저 기록하고 `localSaveVersion`을 증가시킵니다. 클라우드 요청에는 그 시점의 버전을 넘기며, 완료 후 `version == localSaveVersion`일 때만 pending 상태를 변경합니다.

```text
Save A: local version 1, pending = true, upload A 시작
Save B: local version 2, pending = true, upload B 시작

upload A 응답
  version 1 != current 2
  -> pending 상태를 변경하지 않음

upload B 성공
  version 2 == current 2
  -> pending = false를 로컬에 기록
```

클라우드 업로드용 JSON에서는 로컬 전용인 pending 플래그를 잠시 제외합니다. 실패 시 최신 요청에 한해서 pending을 다시 로컬에 남기고, 다음 초기화 때 `SyncPendingLocalSaveToCloudAsync`가 로컬 데이터를 재전송합니다. 클라우드 로드 예외는 경고만 남기고 이미 읽은 로컬 데이터를 유지합니다.

### 검토한 다른 방법

- 모든 업로드를 직렬로 기다림: 순서는 단순해지지만 저장 호출이 네트워크 대기와 결합됩니다.
- 이전 요청 취소: 저장소 구현마다 취소 지원과 실제 서버 반영 시점이 달라 완료 상태의 기준으로 쓰기 어렵습니다.
- 서버 조건부 쓰기 또는 리비전 병합: 여러 기기 충돌까지 다룰 수 있지만 현재 구현 범위와 서비스 계약을 넘어갑니다.

### 실패 시 처리

- 업로드 실패 시 최신 저장 버전이라면 pending을 `true`로 유지하고 로컬에 기록합니다.
- 다음 실행의 재전송도 실패하면 pending을 유지하고 로컬 게임 진행은 계속합니다.
- 클라우드 로드 실패 시 로컬 데이터를 덮어쓰지 않습니다.
- 이 구조는 서버에 도착하는 쓰기 순서를 제어하지 않습니다. 이전 요청의 서버 쓰기가 최신 요청보다 늦게 반영되는 문제나 여러 기기 충돌은 별도 정책이 필요합니다.

## R — Result

정적 코드 확인 결과, 로컬 저장은 클라우드 요청 전에 완료되고, 요청 버전이 현재 로컬 버전과 일치할 때만 동기화 완료 상태를 갱신합니다. 실패한 최신 데이터는 pending 상태로 남아 다음 초기화에서 재시도됩니다.

이번 작업에서는 UGS 실계정으로 응답 순서를 강제로 뒤집거나 다음 실행 재전송을 확인하지 않았습니다. 따라서 “서버 데이터 충돌 방지”가 아니라 “이전 응답에 의한 최신 로컬 완료 상태 오표시 방지”로 범위를 제한합니다.
